Canary reviewer flow: dogfood an unreleased reviewer on a labeled PR, isolated from the production reviewer in both directions. Both workflows post as the same bot identity, so the isolation is two knobs plus one production-side filter.

Canary-side, gated on `REVIEW_CANARY=1` and inert everywhere else: `lib/stage-pr.ts` stages every carrier of the reviewer's own history empty (prior bot reviews without fetching them, bot threads, adjudicated threads) and ignores the cache-memory record, with `runRereviewPlanCli` closing the cache-fallback stamp read too, so the run reviews the whole diff at full depth as a first encounter (human threads still stage, they are PR context, not reviewer history). `runRereviewStampCli` never emits the re-review fingerprint stamp, since a canary stamp would be the newest parseable one in the production reviewer's staging and would anchor its next round's scoping on unreleased code's review. The submission plan (`submission-clearance.ts`) submits every canary verdict as COMMENT with a body Note naming the would-be verdict, because GitHub moves a reviewer's state on APPROVE or REQUEST_CHANGES and under the shared identity a canary APPROVE would supersede the pinned reviewer's standing block while a canary REQUEST_CHANGES would stand with no dismissal path. The dispatch gate accepts blocking inline comments on a canary COMMENT (the demotion is licensed) and blocks any other queued canary verdict (`canary-verdict-not-comment`). `lib/version-footer.ts` gains a `canary <sha>` segment after the version segment, rendered when `REVIEW_CANARY_SHA` is set, so a canary review is attributable to the sha that ran (package.json still carries the last released version on a head checkout).

Production-side, always on: `lib/stage-pr.ts` drops reviews carrying the canary footer segment from `prior-reviews.json` and keeps canary-opened threads out of both thread partitions, so the pinned reviewer never reads canary output as its own history once a release carrying this ships (a canary blocking thread would otherwise feed `keptBlockingCount` and floor the production verdict). The discriminator is one predicate (`hasCanaryFooter`, exported beside the footer renderer so the emitters and the filter cannot drift), matched by both the version footer's `canary <sha>` segment and the same segment `renderAttributionFooter` now appends to inline comments on canary runs. Production consequently never resolves canary threads: a human closes them, or unlabels and addresses.

Khan/actions installs the consumer as `.github/workflows/review-canary.md`, a posting-only variant gated on the `review-canary` label (head-sha lib checkout, COMMENT-only submission, no thread resolution, no reviewer requests, no cache memory), held in sync with the installed `review.md` by `.github/workflows/review-canary.test.ts`.

Expected output-shape effect: none in production runs (the staging filter only removes reviews production never posted). A canary run's bodies carry one extra footer segment (`canary <12-char sha>`, 19 characters) and, when the verdict was demoted, one Note line; canary rounds post full-depth output every push while the label stays on, which is the flow's point.
