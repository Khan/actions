Canary staging mode for dogfooding an unreleased reviewer. With `REVIEW_CANARY=1` in the staging step's env, `lib/stage-pr.ts` stages every carrier of the reviewer's own history empty (prior bot reviews without fetching them, bot threads, adjudicated threads) and ignores the cache-memory record, so the run reviews the whole diff at full depth as a first encounter. Human threads still stage: they are PR context, not reviewer history. Motivation: a canary workflow that runs the reviewer from a PR's own head posts as the same bot identity as the pinned reviewer, so without the knob it would read the production reviewer's reviews, threads, and stamps as its own, scope its round to what the PRODUCTION reviewer covered, and adjudicate threads it never opened. `lib/version-footer.ts` gains a `canary <sha>` segment after the version segment, rendered when `REVIEW_CANARY_SHA` is set, because `package.json` still carries the last released version on a head checkout and the version segment alone would misattribute a canary review. Both knobs are env-gated and off in every production run: no staged shape, posted body, or credit profile changes unless a workflow sets them. Khan/actions installs the consumer of both as `.github/workflows/review-canary.md`, a posting-only variant gated on the `review-canary` label (head-sha lib checkout, no thread resolution, no reviewer requests, no cache memory), held in sync with the installed `review.md` by `.github/workflows/review-canary.test.ts`.

Expected output-shape effect: none in production runs. A canary run's review body and guidance comment carry one extra footer segment (`canary <12-char sha>`, 19 characters), and canary rounds post full-depth output every push while the label stays on (no re-review scoping, no open-thread suppression against the pinned reviewer's threads), which is the flow's point.
