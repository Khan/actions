Adds an opt-in `maintainability` reviewer. It checks whether a change leaves the codebase no harder for the next reader to understand, navigate, or change than it found it, and names five finding types in priority order: a second copy of something that already exists in the repo (both definitions quoted, equivalence stated), a name that misleads (the prediction a reader makes from the name and the line that breaks it), a behavior flag threaded through two or more calls before anything reads it, dead or unreachable code inside a function the diff touched, and an abstraction with one implementation or one caller. Advisory-only and off everywhere until a repo adds `enable maintainability` to its ROUTING file. It reads an optional `symbol-candidates.json` (same-name and same-arity symbols elsewhere in the checkout for each function the diff adds) when a staging step provides one, and falls back to its own bounded grep when the file is absent, so nothing else changes until that step lands.

Its findings render with a new non-blocking label, `suggestion (non-blocking, maintainability)`, for the same reason `documentation` has one: the label is the only channel by which a consumer reading posted threads can tell these findings apart, and they are the shape a scoped autofix does well. The label joins `NON_BLOCKING_LABELS`, so `autofix: nits` covers it by inclusion once the autofix pin moves to a release carrying it (an installed autofix reads `NON_BLOCKING_LABELS` from its own pinned tag, which a review-only release does not move, the same coupling the `docs` scope shipped with). Expected output-shape effect in a repo that enables it: up to five additional advisory findings per review carrying the new label, competing for the same non-blocking inline budget (default 3) and otherwise landing in the review body's collapsed observations, and nothing in a repo that does not.

Supporting changes: a maintainability-claim rule for the claim-validator whose refutation case is a "duplicate" whose existing counterpart differs in error handling, a type, or a side effect; `holistic`'s do-not-duplicate list names the new reviewer; the low-tier invocation cap moves from 8 to 9 so a lens-free low-tier run still dispatches the two defaults plus every opt-in (router.test.ts pins the cap to the roster size); and the eval corpus gains five golden cases, one per finding type, each seeded inside a diff that does real logic work, plus a clean case whose change reuses the existing helpers and must draw nothing. None carries the `smoke` tag, so the per-PR A/B skips them; price the reviewer with a targeted `workflow_dispatch` of *Review Eval A/B* over the six cases.
