Adds an opt-in `maintainability` reviewer. It checks whether a change leaves the codebase no harder for the next reader to understand, navigate, or change than it found it, and names five finding types in priority order: a second copy of something that already exists in the repo (both definitions quoted, equivalence stated), a name that misleads (the prediction a reader makes from the name and the line that breaks it), a behavior flag threaded through two or more calls before anything reads it, dead or unreachable code inside a function the diff touched, and an abstraction with one implementation or one caller. Advisory-only and off everywhere until a repo adds `enable maintainability` to its ROUTING file. It reads an optional `symbol-candidates.json` (same-name and same-arity symbols elsewhere in the checkout for each function the diff adds) when a staging step provides one, and falls back to its own bounded grep when the file is absent, so nothing else changes until that step lands.

Its findings render with a new non-blocking label, `suggestion (non-blocking, maintainability)`, for the same reason `documentation` has one: the label is the only channel by which a consumer reading posted threads can tell these findings apart, and they are the shape a scoped autofix does well. The label joins `NON_BLOCKING_LABELS`, so `autofix: nits` covers it by inclusion once the autofix pin moves to a release carrying it (an installed autofix reads `NON_BLOCKING_LABELS` from its own pinned tag, which a review-only release does not move, the same coupling the `docs` scope shipped with). Expected output-shape effect in a repo that enables it: up to five additional advisory findings per review carrying the new label, competing for the same non-blocking inline budget (default 3) and otherwise landing in the review body's collapsed observations, and no maintainability findings in a repo that does not enable it. Separately, the low-tier invocation-cap increase can dispatch an existing reviewer that was previously shed, even when maintainability remains disabled.

Supporting changes add a validator rule that refutes duplicates with different error handling, types, or side effects, and name maintainability in holistic's do-not-duplicate list. The low-tier invocation cap moves from 8 to 9 so a lens-free low-tier run fits the two defaults and every opt-in. The corpus includes the original six screening cases and 20 additional synthetic cases across nine families, all requesting the full consumer roster and none tagged smoke. Matched counterexamples cover incompatible types, errors, side effects, justified indirection, and reachable code. Mixed-reviewer cases exercise inline and invocation pressure. Four cases are reserved from routine live runs. Recorded references, behavioral checks, diff reconstruction, source hashes, and fixture typechecks calibrate the corpus, not model usefulness. Enabling the reviewer still requires an explicitly approved full-roster comparison that separates cap recovery from unique useful catches, overlap, false positives, cost, and displaced coverage.
