Open-thread suppression attributed a candidate to the FIRST staged thread it cleared the similarity floor against rather than the best-matching one, and since `threadBlocking` is read off that thread, staging order could decide the verdict. Measured on webapp#41204 run 30650642317, the first live run in which suppression fired at all (six suppressions against a non-empty reconciler `keep` list): the fresh test-adequacy todo "No test covers Record's documented zero-valued-Window guarantee" cleared the floor against both the blocking nil-map panic thread and its own exact counterpart, a non-blocking `nitpick` whose opener reads "The documented zero-value-Window guarantee has no test". The blocking thread was staged first because it was older, so the suppression recorded `threadBlocking: true` and contributed a second entry to `submission.ts`'s verdict floor. That run's REQUEST_CHANGES was already correct on the strength of another suppression, so nothing was mis-decided, but the error direction is the dangerous one: attributing a candidate to a blocking thread that is not its match forces REQUEST_CHANGES on thinner evidence than the both-sides-blocking rule intends, and the same ordering accident can hand a candidate a non-blocking thread when a blocking one is its real counterpart, silently lowering the floor. `suppressOpenThreadDuplicates` now ranks every thread that clears the floor and takes the best, on `jaccard` first because it is the length-normalized metric (raw `sharedBigrams` grows with the opener's length, and `overlap` divides by the smaller token set, so both favor the longer, more discursive thread); on the observed pair jaccard 0.253 vs 0.218 and bigrams 13 vs 12 both pick the true counterpart while overlap alone, 0.468 vs 0.511, picks the wrong one, so bigrams break jaccard ties and overlap never ranks. Comparisons are strictly-better, so staging order remains the final tiebreak and an exact scoring tie behaves as before, keeping `dispatch-result.json` reproducible. The regression case stages the blocking thread first, exactly as the live run did, and asserts the same attribution both ways round.
